# Инфраструктура ML-проекта

Домашнее задание №1. Проект создан через `uv init --lib` со структурой `src/`.
Python зафиксирован на 3.12.8; зависимости и версии инструментов — в `uv.lock`.

## Установка и запуск

Требуются macOS или Linux, Git, make, curl и доступ к интернету при первом запуске.
После клонирования перейдите в корень репозитория:

```sh
make setup
make check
make demo
```

`make setup` автоматически устанавливает uv, если он отсутствует, загружает нужный Python,
создаёт `.venv`, устанавливает зависимости строго по lock-файлу и подключает pre-commit.
Активация окружения не требуется. Повторный запуск безопасен.

| Команда | Назначение |
| --- | --- |
| `make setup` | Поднять окружение и установить хуки |
| `make check` | Проверить стиль, форматирование и типы без исправлений |
| `make hooks` | Запустить все хуки на всём проекте |
| `make demo` | Запустить демонстрацию; результат `Accuracy: 75.00%` |

## Структура

- `src/ml_product_infrastructure/` — типизированный код проекта и расчёт accuracy.
- `scripts/debug_checks.py` — отладочный скрипт с аннотированной функцией.
- `scripts/uv.sh` — автоматическая подготовка uv для чистой машины.
- `.github/workflows/checks.yml` — проверки pull request и main в GitHub Actions.
- `docs/` — история работы с ветками и инструкция по защите main.

## Проверки

Ruff 0.14.0: длина строки 99, дополнительные группы B, UP, I, SIM;
F401 игнорируется в `__init__.py`. Форматтер запускается только с `--check`.
Mypy 1.18.2 работает в strict-режиме. Исключение для отсутствующих аннотаций
задано только для стороннего pandas; собственные импорты и функции проверяются строго.
Pre-commit 4.3.0 запускает инструменты из того же lock-файла, что и `make check`.
Все три хука выполняются на каждом коммите и возвращают ошибку при нарушениях.

Для проверки испортите тип аргумента в `scripts/debug_checks.py` или добавьте
неиспользуемый импорт: `make check` и попытка коммита должны завершиться с ошибкой.
Перед продолжением восстановите корректный код.

## Данные — ДЗ №2

### Подготовка и полный запуск

Нужны работающие Docker Engine и Compose v2+ (`docker compose version`), примерно
3 ГБ свободного места и интернет для первого запуска. На macOS можно использовать
Docker Desktop либо Colima с Docker CLI и Compose; сначала запустите среду контейнеров.
После клонирования из корня проекта:

```sh
make setup
make check
make s3-up
make ingest
make data
```

`make setup` создаёт `.env` из `.env.example`, если файла ещё нет. Значения в существующем
`.env` сохраняются; недостающие настройки добавляются из примера. Адреса, порты, бакет и реквизиты S3 берутся из окружения/`.env`.
Параметры обработки лежат в `configs/data.json`. Данные и реальные реквизиты Git игнорирует.

`make s3-up` поднимает **RustFS 1.0.4**, ждёт его healthcheck, собирает init-контейнер
и автоматически создаёт бакет. Для просмотра откройте [консоль RustFS](http://127.0.0.1:9001)
и войдите с `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` из своего `.env`.
S3 API по умолчанию доступен на `http://127.0.0.1:9000`.
[Документация RustFS](https://docs.rustfs.com/en/installation/container/docker).

```sh
make s3-down     # остановить контейнеры, сохранив именованные volumes
make s3-up       # вернуться к прежним данным; бакет повторно не создаётся
```

Не используйте `docker compose down -v`, если хотите сохранить данные: `-v` удаляет
volumes. Обычный `make s3-down` этого флага не содержит.

Если Compose установлен отдельной командой, используйте `make s3-up COMPOSE=docker-compose`
и такой же параметр для `make s3-down`.

### Независимые шаги

| Команда | Действие |
| --- | --- |
| `make ingest` | Официальный архив → `raw/` в S3 без распаковки |
| `make data-download` | S3 → `data/raw/`, проверка SHA-256 |
| `make data-convert` | Проверенный pickle → 60 000 RGB PNG и исходная JSON-разметка |
| `make data-split` | Стратифицированные train/val; test и PNG не меняются |
| `make data-stats` | Mean и population std RGB только по train, значения пикселей / 255 |
| `make data-publish` | Проверка хешей, сборка manifest, параллельная выгрузка новой версии |
| `make data` | Все пять шагов обработки подряд |
| `make test` | Тесты разбиения, статистик, валидации и неизменяемых записей |
| `make test-s3` | Контрактные тесты настоящего RustFS после `make s3-up` |

Каждый шаг — отдельный Python-модуль и CLI. Например:

```sh
sh scripts/uv.sh run python -m ml_product_infrastructure.dataset.split --help
sh scripts/uv.sh run python -m ml_product_infrastructure.dataset.split --seed 123 --val-size 6000 --version v2
```

Все шаги принимают `--config`, `--version`, `--seed`, `--val-size`, `--workers`.
Через Make параметры передаются без изменения кода:

```sh
make data DATA_ARGS="--version v2 --seed 123 --val-size 6000"
# Или передать другой JSON-конфиг:
make data CONFIG=configs/data.json DATA_ARGS="--version v3 --seed 7"
```

Перед публикацией код должен быть закоммичен: иначе конвейер завершится понятной
ошибкой, чтобы `git_commit` точно указывал использованный исходный код. Клонированная
main уже удовлетворяет этому условию. Изменённый конфиг также нужно закоммитить
в рабочей ветке; изменения CLI не требуют коммита.

### Что хранится в S3

В бакете `cifar10` по умолчанию:

```text
raw/cifar-10-python.tar.gz
processed/cifar10/v1/
    images/train_00000.png ... train_49999.png
    images/test_00000.png  ... test_09999.png
    annotations/train.json
    annotations/val.json
    annotations/test.json
    stats.json
    manifest.json
_locks/processed/cifar10/v1.json
```

`make ingest` сначала проверяет объект в S3. Если он уже существует, нет ни повторного
скачивания, ни загрузки. Запись raw использует `If-None-Match: *`, поэтому параллельный
запуск также не перезапишет объект. Архив перед загрузкой и перед чтением pickle
сверяется с фиксированным SHA-256 в конфиге. В S3 сохраняются исходные байты gzip.

В JSON-разметке: `classes`, затем `images` с `image_id`, `file_name`, `label`,
`label_name`, `sha256` байтов PNG. Валидационные картинки сохраняют имена `train_…`.
Локальные `_train_full.json` и `_conversion.json` нужны для повторения шагов и в S3 не
выгружаются. По умолчанию локальный результат находится в `data/processed/cifar10/v1/`.

В `stats.json` сохранены `mean`, `std`, RGB-порядок каналов, масштаб, число изображений
и SHA-256 использованной train-разметки. В `manifest.json` — числа изображений по
выборкам, размеры и SHA-256 трёх разметок и статистик, seed, val_size, источник,
версия и git-коммит обработки. Сами PNG проверяются по хешам из разметки.

Существующий префикс версии блокируется **до** обработки. Для защиты от одновременных
запусков создаётся неизменяемая резервация в `_locks/`; каждый объект записывается
условно. `manifest.json` записывается последним и служит признаком завершённой версии.
При прерванной выгрузке отсутствует manifest; повторный запуск не затирает частичные
данные и просит новое имя версии. То же относится к повторному `make data` после успеха.

### Краткая карточка CIFAR-10

- Источник: [официальная Python-версия CIFAR-10](https://www.cs.toronto.edu/~kriz/cifar.html),
  Alex Krizhevsky, Vinod Nair, Geoffrey Hinton. Ссылка на архив и его SHA-256 зафиксированы
  в конфиге. Официальный MD5 архива: `c58f30108f718f92721af3b95e74349a`.
- 60 000 цветных изображений 32×32: исходные train 50 000 и test 10 000.
- Классы в порядке меток 0–9: airplane, automobile, bird, cat, deer, dog, frog, horse,
  ship, truck.
- Наше разбиение при seed 42: **45 000 / 5 000 / 10 000**. На класс приходится
  4500 train, 500 val и 1000 test. Исходный test не участвует в разбиении и нормализации.
- Ограничения: маленькое разрешение, десять заданных классов, неоднозначные визуальные
  примеры. Конвейер сохраняет исходные метки и не удаляет визуальные дубли; результаты
  на этом учебном наборе не описывают качество на произвольных фотографиях.

Для ссылок в учебных работах: Alex Krizhevsky, *Learning Multiple Layers of Features
from Tiny Images*, 2009 (отчёт доступен на официальной странице датасета).

Полный прогон двух версий, идемпотентность, сохранность volumes и независимая проверка
нормализации зафиксированы в [отчёте ДЗ №2](docs/hw2-verification.md).


## Эксперименты — ДЗ №3

### Запуск инфраструктуры и серии

Используются CPU PyTorch 2.9.0 и MLflow 3.16.0. На Linux uv берёт CPU-колесо из
официального индекса PyTorch; зависимости зафиксированы в uv.lock. MLflow хранит
метаданные в SQLite на именованном volume `mlflow-db`, артефакты — в отдельном
S3-бакете `mlflow`. Оба хранилища сохраняются при обычном `infra-down`.

Из чистого checkout (код должен быть закоммичен):

```sh
make setup
make infra-up
# Если processed/cifar10/v1 ещё нет, выполнить шаги ДЗ №2:
# make ingest
# make data
make experiments CONFIG=configs/grid.json
```

Интерфейс: [MLflow](http://localhost:5000). Адреса, допустимые Host и реквизиты
передаются через `.env`; для контейнеров используются адреса внутри общей сети
Compose. MLflow проксирует артефакты в S3; клиенту не нужны ключи для обращения
к трекеру (S3-ключи в trainer используются отдельно для данных и моделей).
`make infra-up` автоматически создаёт отдельный бакет артефактов, ждёт healthcheck
MLflow и собирает обучающий образ по lock-файлу. Дополнения сервера описаны в
`docker/mlflow.Dockerfile`, Dockerfile в корне предназначен для обучения.

```sh
make train CONFIG=configs/train.json  # один запуск с именем из конфига
make infra-down                     # остановить всё, сохранив volumes
```

Для повторения одиночного запуска укажите новое `run_name` в JSON, чтобы не
перезаписывать уже сохранённые результаты. Сетка автоматически добавляет уникальный
суффикс серии. Каждый baseline, элемент сетки и итоговый запуск выполняется в
**отдельном контейнере**, подключённом к S3 и MLflow. Кеш PNG между контейнерами
общий (`train-cache`); для каждой версии проверяются manifest, размеры и SHA-256.
Исходный код запекается в образ; его git-коммит проверяется при запуске.

### Конфиги, протокол и артефакты

`configs/train.json` задаёт полный конфиг запуска: эксперимент, имя, seed, S3-версию,
лимит train, тип/размеры модели, эпохи, batch size, LR, weight decay и число CPU-потоков.
Поддержаны `linear` (3072 → 10) и `simple_cnn` (2–3 Conv/ReLU/MaxPool и классификатор).
`configs/grid.json` содержит базовый конфиг, dotted-параметры сетки и настройки
итогового запуска. Их можно менять без правок кода; изменения файлов нужно
закоммитить в рабочей ветке перед сборкой, либо передать другой сохранённый конфиг.

По умолчанию baseline и шесть CNN обучаются 3 эпохи на одной фиксированной
стратифицированной подвыборке из 10 000 train-изображений. Сетка: LR
`0.0003 / 0.001 / 0.003`, batch `64 / 128`. Лучшая конфигурация выбирается по
минимальному validation loss, затем обучается с нуля на полном train 8 эпох.
Валидация и test не сокращаются. Нормализация — только из stats.json выбранной
S3-версии; seed, порядок обучения и CPU-алгоритмы фиксируются.

В MLflow для каждого запуска сохраняются все поля конфига как параметры, полный
config.json, версия/manifest данных, git-коммит, метрики val по эпохам, время,
номер лучшей эпохи, итоговые test-метрики, веса и таблица матрицы ошибок
`confusion-val.csv` (строки — истинный класс, столбцы — предсказание).
Точность и macro-F1 считаются по фиксированным десяти классам.

Чекпоинт обновляется только при уменьшении val loss. После обучения он
восстанавливается; test оценивается один раз и не участвует ни в выборе эпохи,
ни в ранжировании сетки. Веса загружаются с `weights_only=True`.

В бакете данных: `models/<experiment_name>/<run_name>/model.pt`, `config.json`,
`metrics.json`. Чекпоинт также содержит архитектуру, классы и нормализацию для
следующей домашки. Имена запусков не перезаписываются. Сводка серии сохраняется
в `models/<experiment_name>/suites/<suite_id>/summary.json`, локально — в
`data/experiments/<suite_id>/summary.json` и `results.md`. В metrics.json записан
ID контейнера и число итоговых test-оценок для проверки протокола.

CI дополнительно обучает две эпохи в настоящем отдельном контейнере на крошечной
изолированной fixture-версии и проверяет MLflow, сохранённый лучший чекпоинт и S3.
Эта fixture не входит в отчёт экспериментов на настоящем CIFAR-10.
